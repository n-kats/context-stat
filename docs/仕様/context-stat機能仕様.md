# context-stat 機能仕様

この文書は現行版の機能仕様である。利用者向けの実行例は`../手順/context-statを使う.md`、実装済み範囲と制約は`../現状/context-statの現状.md`を参照する。仕様にないコマンドは提供しない。

## 目的

`context-stat` は、コーディングエージェントがコンテキストに含める可能性のある情報を、実際の入力または実機実行から計測するローカルツールである。

対象はファイルだけに限らず、コマンド結果、テンプレートのレンダリング結果、Gitの差分、MCPのリクエストとレスポンスを含む。

## 基本方針

- 1回の入力または実機実行を、その場で計測する。
- 計測結果を蓄積して利用履歴や利用回数を集計しない。
- 外部へのテレメトリ送信を行わない。通常の計測はローカルで完結させる。
- 外部の計測APIを使うバックエンドを追加する場合も、明示指定時だけ使用する。明示指定による入力の送信はテレメトリではなく、ユーザーが要求した計測処理として扱う。
- ディレクトリを対象にした場合は、既定でGitのignore規則を反映して対象外ファイルを除く。`--ignore-gitignore`を指定した場合はignore規則を無視する。再帰列挙ではGit管理メタデータの`.git`ディレクトリは対象にしない。直接指定したファイルはignore規則に関係なく対象にする。
- 入力を生成したツールに依存せず、計測対象の内容と計測条件を結果に反映する。

## 計測項目

計測可能な項目として、次を定義する。

- バイト数
- 文字数
- 行数
- トークン数
- 入力項目数
- 最長行の長さ
- 項目ごとの値
- 合計値

計測項目はルート共通オプションの`--metrics`で選択する。既定値は`token`で、テキストの`tokens`と画像の`image_tokens`だけを計測する。`--metrics all`では、実装済みのバイト数、文字数、行数、最長行、トークン数、画像属性、パス長を計測する。複数項目はカンマ区切りで指定でき、選択されていない項目は計算せず、出力にも含めない。

トークン数は、モデル名から推測せず、指定したテキストトークナイザーを基準に計測する。計測対象は実際の生テキストとし、LLM向けのチャット形式、role、system prompt、API固有のラッパーや追加文字列を計測のために付加しない。使用したバックエンドとトークナイザーは計測条件として結果へ記録する。

テキスト用トークナイザーは `--text-tokenizer` で指定し、既定値は`tiktoken`の`o200k_base`とする。画像用の計測方式は通常のテキストトークナイザーとは分け、`--image-tokenizer`で指定する。既定値は`gpt-5.6-style`とする。モデル名から計測方式を自動選択しない。

現時点の標準方式は、テキストが`tiktoken:o200k_base`、画像が`gpt-5.6-style`である。現行版で実装している画像方式名は`gpt-5.6-style`だけである。この方式は元画像を32x32ピクセルのパッチで覆うために必要な数を`ceil(width / 32) * ceil(height / 32)`で求め、画像トークン数とする。context-stat自身は画像をリサイズしない。将来方式を追加する場合も、方式名、計算規則、根拠、テストを一体で定義する。

### バックエンド

テキスト計測に使用する実装を `--backend` で切り替える。`--backend` を省略した場合は `auto` とする。

- `auto` は `tiktoken` を明示的に選択する。モデル名に応じて別のバックエンドへ黙って切り替えない。
- `auto` が外部の計測APIを選択して、入力を暗黙に外部送信してはならない。
- 現在の標準バックエンドはローカルで動作する`tiktoken`であり、入力を外部へ送信しない。

現行版のバックエンドは、標準依存の`tiktoken`とextraで導入する`tokenizers`だけである。高速実装などは現行版の選択肢ではなく、追加する場合に方式、依存、テストを別途定義する。`auto`は`tiktoken`を選択し、他のバックエンドは明示指定する。

`--backend` はテキスト計測の実装を指定し、`--text-tokenizer` はそのバックエンドで使用するトークナイザーやエンコーディングを指定する。`--image-tokenizer`は画像の計測方式を指定する。3つの指定と実際の計測方式を結果に記録する。

計測結果には、要求されたバックエンド、実際に使用したバックエンド、計測状態（`measured`、`skip`、`failed`）および外部送信の有無を含める。値がない場合は`skip`または`failed`とし、理由を警告またはエラーとして返す。`exact`や`estimated`の精度表示は設けない。

### オプション依存関係とインストール

標準インストールにはClick、tiktoken、MCPクライアント機能に必要な公式Python SDKをコア依存として含める。tokenizersなど、選択式のバックエンド依存だけをPythonパッケージのextrasとして個別に導入する。

例:

```text
uv tool install "context-stat[tokenizers]"
```

高速実装など追加のバックエンドも、それぞれ対応するextraを指定して導入する。extrasを指定しない標準インストールでも、tiktokenによるテキスト計測、バイト数・文字数・行数などの基本計測、MCPサーバーへの接続・一覧取得・リクエスト実行を利用できる。tokenizersを使う計測には対応するextraが必要になる。

現行実装で提供するテキストバックエンドは、標準依存の`tiktoken`と、extraで導入する`tokenizers`である。オンライン型のToken Count APIアダプターは現行版には実装しない。モデル固有の方式名と入力条件が確定した場合に、別のバックエンド追加として扱う。

要求されたバックエンドのextraが導入されていない場合は、自動インストールや別バックエンドへの黙った切り替えを行わず、必要なextraを案内してエラーにする。

`--allow-online` は、将来追加する入力送信型のトークナイザーまたは計測バックエンドを許可する実行時オプションである。オンライン用extraの導入やバックエンド設定を代替するものではない。現行版にはオンライン計測バックエンドがないため、この指定による入力送信は発生しない。オンライン方式を追加する場合は、この指定がなければ入力を送信する前にエラーにする。現行の`tiktoken`、`tokenizers`、MCP接続には適用しない。MCPの接続可否や接続方式とは関係しない。

画像のトークン数は通常のテキストトークナイザーでは計測せず、`--image-tokenizer`で指定した画像計測方式に従う。任意の画像ライブラリでリサイズした結果をトークン数の根拠にはしない。画像方式と計測条件を結果に明記する。

## 入力種別

### ファイルとディレクトリ

ファイル名またはディレクトリ名を対象にする。ディレクトリは再帰的に対象とし、ファイルごとの計測結果と全体の集計結果を返す。

非画像のバイナリファイルはテキスト計測の対象から除外し、除外したパスを警告と事実情報へ記録する。UTF-8として解釈できないファイル、またはNULバイトを含むファイルを非画像バイナリと判定する。画像として認識できるファイルは、画像の入力条件に従って扱う。

ファイルを直接対象にした場合は、次を確認できるようにする。

- ファイル数
- ファイルごとのバイト数、行数、文字数、トークン数
- パスの長さ
- トークン数やサイズが大きいファイル
- 合計値

`-` は標準入力を表し、標準入力に渡されたテキストを1つの計測対象として扱う。

### 画像

画像も計測対象とする。

- 画像ファイルを直接指定した場合は対象に含める。
- ディレクトリを再帰的に対象にする場合は、`--include-images` が指定されたときに画像を含める。
- ディレクトリを再帰的に対象にする場合は、既定で`.gitignore`を反映し、`--ignore-gitignore`で無視できる。
- 元ファイルのバイト数、形式、幅、高さ、フレーム数などの画像属性を最初に計測する。
- 画像トークン数の算出と、画像が計測方式の上限を超えた場合の扱いを別の概念として扱う。
- トークン数は、元画像の寸法または画像方式で定義された有効寸法に対して、方式固有の算出規則を適用する。補間法などのリサイズ方式そのものは計測条件にしない。
- context-statが任意のリサイズ方式を選び、画像を書き換えてから数えることはしない。公式仕様が上限超過時の有効寸法を定めている場合だけ、その寸法への正規化を計算上の規則として扱う。
- 画像方式には、対応形式、最大ファイルサイズ、最大幅・高さ・長辺、画像数上限、detailや解像度モード、画像トークン数の算出規則、上限超過時の扱いを定義する。
- 公式仕様がプロバイダー側のリサイズ、アスペクト比維持、パディングなどを算出規則に含めている場合は、その正規化後の有効寸法を方式の決定的な計算として実装する。汎用画像ライブラリにその判断を委ねない。
- context-statは入力画像をリサイズしたファイルとして保存したり、元画像を上書きしたりしない。
- 結果では、元画像の属性、画像方式上の制約、有効寸法（算出できる場合）、画像トークン数、上限判定、上限超過時に適用した扱いを分けて表示する。
- 上限超過時の扱いは画像方式ごとに定義する。少なくとも、仕様上プロバイダーが受理して内部正規化する場合、プロバイダーが拒否する場合、ローカルでは判定できずオンライン計測が必要な場合、対応外の場合を区別する。
- 上限を超えた画像を、理由を表示せず別のサイズや別の形式として黙って計測しない。ローカルで画像方式を再現できない場合は、推定値を返さず、計測値を`skip`として理由を警告へまとめる。
- 現在の既定方式`gpt-5.6-style`は、対応形式の正常な静止画像について画像トークン数を計測する。GPT-5.6の画像入力で対応されるPNG、JPEG、WEBP、非アニメーションGIF以外の形式、アニメーションGIF、未実装の画像方式、画像として読み取れない画像の画像トークンは`skip`として警告にまとめる。画像属性を要求していて読み取りに失敗した場合は、属性計測を`failed`としてエラーにする。入力データの大きさが既知のリクエストペイロード上限を超える場合は、トークン数を返したうえで上限状態を`over`とする。

画像を含むディレクトリを対象にした場合、元画像の属性と画像方式適用後の計測値の両方を確認できるようにする。MCPレスポンスに含まれる画像contentも同じ考え方で計測する。

#### 画像計測方式

現行版で実装している画像計測方式は`gpt-5.6-style`だけである。追加方式を実装する場合は、テキスト用トークナイザーとは別の方式として、次の情報を定義する。方式は、特定モデルの公式な計算式を意味する場合と、互換性を意図した方式を意味する場合がある。

- 方式名と対象とする入力仕様
- 受け付ける画像形式とアニメーションの扱い
- ファイルサイズ、幅、高さ、長辺、画像枚数などの上限
- detail、解像度、品質など、入力指定によって計測条件が変わる項目
- 元画像から画像トークン数を求める算出式
- 上限超過時にプロバイダーが行う処理、または拒否する条件
- ローカルで再現可能か、外部の計測APIが必要か
- 参照した公式仕様と、その確認時点

画像方式はライブラリの既定値をそのまま採用せず、公式仕様に基づくコードとテストで管理する。画像ライブラリを使用する場合も、形式判定や寸法取得などの入力観測に限定し、方式ごとの上限判定、正規化、トークン算出の責任はcontext-stat側に置く。

### ファイルごとのコマンド実行

ファイルまたはディレクトリを対象に、パスをJinja形式の変数としてコマンドを生成し、各ファイルに対するコマンドの出力を計測できるようにする。ディレクトリ再帰時の画像選択は通常のファイル計測と同じく、`--include-images`がなければ画像を除外し、拡張子だけでなく内容から認識できる画像も対象にする。

例として、コマンドテンプレート内で `{{path}}` を対象ファイルのパスとして利用する。コマンドの標準出力を計測対象とし、標準エラー出力と終了状態は実行結果として扱う。

レンダリング後のコマンド文字列は、シェルとして実行せず、shell-likeな引用を`shlex.split`でargvへ変換して`shell=False`で実行する。パイプ、リダイレクト、コマンド置換、シェル変数展開は解釈しない。任意のパスを安全に埋め込むため、正式な推奨形としてJinjaの`quote`フィルターを用意する。

標準出力だけを計測対象本文とし、標準エラー、終了状態、実行時間、タイムアウトを実行結果として分ける。ディレクトリ内の一部のコマンドが失敗しても他の対象の計測を継続し、全体の終了状態にはエラーがあることを反映する。タイムアウト時はプロセスグループを終了し、出力サイズにも上限を設ける。出力を切り詰めた場合は、切り詰め状態を対象の実行結果と診断へ記録する。

### Jinjaレンダリング

Jinja形式のテンプレートとJSON形式のパラメータを受け取り、レンダリング結果を計測する。

テンプレートそのものではなく、実際に生成された結果を計測対象とする。

### Git差分

Gitの差分を標準入力として受け取るのではなく、ローカルのGit情報から直接取得する。最初に対応するGit操作は `diff` とする。

`context-stat git diff` は、`git diff` と同じ引数の構文を受け付ける。引数を未解釈のままGitへ渡すのではなく、context-stat側のGit差分専用パーサーが解釈、検証、正規化する。patch本文を生成しない`--no-patch`、`--name-only`、`--name-status`、`--stat`、`--numstat`、`--dirstat`、`--summary`、`--check`、`--quiet`などの出力モードは、ファイル単位patchへ変換できないため拒否する。

パーサーは少なくとも次を扱う。

- Git diffのオプションとオプション値
- 比較対象のrevision（0個、1個、2個、またはGitが認めるrevision指定）
- Git diff本来の `--` によるrevisionとpathspecの区切り
- pathspec
- ブランチなどの比較対象が指定されない場合の既定動作

パース結果から安全なargvを組み立ててローカルの `git diff` を実行する。未知またはcontext-statが対応していないGit引数は、未解釈のまま実行せずエラーにする。Gitがリポジトリ状態、revisionの存在、pathspecの妥当性を検証する部分は、Gitの実行結果として扱う。

例えば、次の指定を受け付ける。

```text
context-stat --backend tiktoken --text-tokenizer o200k_base git diff branch branch -- file
```

この場合、`--backend`と`--text-tokenizer`はcontext-statが解釈し、`branch branch -- file`はGit差分パーサーが解釈したうえで `git diff` のargvを生成する。

差分全体に加え、次を計測対象とする。

- 変更されたファイル数
- 追加行数
- 削除行数
- ファイルごとの差分量
- 差分全体のバイト数、行数、文字数、トークン数

差分patchは`diff --git`のファイル単位に分割し、各ファイルのpatch本文を個別の計測対象とする。したがって、通常の`git diff`ではtable、JSON、treeの各itemが変更ファイルに対応し、トークン数もファイルごとの差分patchに対する値になる。差分全体を1つの合成itemとして表示しない。

Git差分の対象範囲や比較対象の指定方法は、Git差分パーサーが扱う引数の仕様に従う。

### MCP

MCPサーバーの設定とパラメータを受け取り、context-statが実際にMCPサーバーへ接続して処理を実行する。MCPサーバー自体をcontext-statに組み込む機能や、MCP形式の記録ファイルを直接集計する機能は対象としない。

MCPのJSON-RPC、初期化、能力交渉、標準transportの処理は、公式Python SDKをcontext-statのアダプター越しに利用する。context-statがMCPプロトコルを全面的に再実装しない。

現行版は、ローカルプロセスを起動するstdioと、ネットワーク上のサーバーへ接続するStreamable HTTPに対応する。旧HTTP+SSEは追加しない。MCPの接続方式はMCP設定で指定する。

stdioはcontext-stat自身のネットワーク接続としては扱わないが、起動したMCPサーバー自身の外部通信までは制御しない。Streamable HTTPも設定された接続先へ通常どおり接続する。

#### 一覧取得

MCPサーバーが提供するツール、リソース、プロンプトなどを取得し、定義、説明、パラメータ定義、Schemaのサイズとトークン数を計測する。

一覧取得では、通常、ツールそのものの実行は行わない。

#### リクエスト実行

指定されたMCPリクエストを実行し、送信側と返却側を分けて計測する。

- `direction`が`client_to_server`で`semantic_role`が`generated`の論理リクエストとパラメータ
- `direction`が`server_to_client`で`semantic_role`が`returned`のツール結果、resource内容、prompt内容、一覧定義
- 返却されたtext、image、structuredContentなどのcontent
- 実行時間
- エラーと警告

MCPのinitialize、initialized、JSON-RPC envelope、通知などのprotocolメッセージは、generated/returnedのコンテキスト合計へ自動加算しない。公式SDKからwire-levelの値を取得できない場合、protocol計測は`skip`として扱い、取得できる論理値から推定しない。

MCPの一覧定義、レスポンス全体、content本文は計測対象の単位を明示し、envelope全体とcontent本文を同じ合計へ二重計上しない。

MCPに渡すパラメータは、LLMが生成する側の入力を再現するための値として扱う。これにより、実際のLLMの生成トークン数やAPI利用量を計測するものではない。

## 出力

計測結果は、人間が確認できる形式と機械処理できる形式の両方を扱えるようにする。

出力には、可能な限り次を含める。

- 入力種別
- 対象名
- 計測条件
- 要求されたバックエンドと実際に使用したバックエンド
- 計測状態と外部送信の有無
- 項目別の値
- 合計値
- 警告
- エラー

MCPでは、リクエストとレスポンスを区別して表示する。

出力形式は`--format`で選択する。既定値は表形式の`table`、機械処理向けは`json`、sourceを根、グループと対象を親子関係で表示する木構造は`tree`とする。treeは標準的なtree表示の罫線（`├──`、`└──`、`│`）で表示し、対象は`path [XX tokens]`のように1行で表示する。skipやfailedの注記を対象ごとの行へ付けず、計測完了後の標準エラーへ集約する。同じ階層の兄弟は`--sort`と`--order`で指定した順序に従う。`--sort`の既定値は`path`、`--order`の既定値は`asc`とする。後方互換のため`--output-format`も同じ値を受け付ける。JSONは`schema_version`を持つ版管理された形式とし、現行版の構造を次で定義する。

ファイルまたはディレクトリを表形式で出力する場合、ディレクトリ自身を集計行として表示する。入力が`.`なら集計行のパスも`.`とし、配下のディレクトリにも同じ規則を適用する。`TOTAL`という合成行は出力しない。tableとJSONのpath groupは、ディレクトリ合計を含む全ノードをフラットな行一覧として出力する。JSONでは、個別ファイルの互換用`items`に加えて、この行一覧を`nodes`として出力する。`nodes`の`kind`は`dir`または`file`、ディレクトリの`metrics`は配下のファイルから集計した値とする。`totals`という合成フィールドは出力しない。
tableの計測値セルは値だけを表示し、単位は列見出しで示す。メトリクス列は右寄せ、パス・項目名・種類の列は左寄せとする。`skip`、`failed`、`external`などの注記を対象ごとに繰り返さない。状態と外部送信の有無はJSONのmetric情報に保持し、skipやfailedの警告・エラーは標準エラーへ集約する。

警告とエラーは通常のレポート出力へ混ぜず、レポートを標準出力へ出し切った後に標準エラーへまとめて出力する。これによりJSONの標準出力を機械処理へそのまま渡せるようにする。

### JSON出力の現行スキーマ

現行の`schema_version`は`1`とする。最上位は`schema_version`、`source`、`request`、`groups`、`facts`、`warnings`、`errors`を持つ。`groups`の各要素は`name`、`items`、`facts`を持ち、ファイルまたはディレクトリを入力したpath groupには`nodes`を付加する。path group以外で計測済みの集計値がある場合は、`summary`にグループ全体のメトリクスを保持する。

`items`の要素は`id`、`origin`、`label`、`kind`、`direction`、`semantic_role`、`limit_status`、`metrics`、`metadata`を持つ。`metrics`の各値は`value`、`unit`、`status`、`external`を必須とし、値がある場合だけ`method`、`reason`、`details`を持つ。`status`は`measured`、`skip`、`failed`のいずれかである。`direction`、`semantic_role`、`limit_status`は対象に該当しない場合は`null`になる。

path groupの`nodes`は、ディレクトリ合計を含む表示順のフラットな一覧であり、各要素は`path`、`kind`、`metrics`を持つ。ファイルnodeには対応する`item`も付加する。ディレクトリの`metrics`は配下の計測済みファイルから集計し、加算項目は合計、`max_line_length`は最大値とする。`TOTAL`行や`totals`フィールドは設けない。path group以外のtableでは、グループ名を集計行として先頭に表示し、`summary`と同じ集計値を示す。警告とエラーはJSONにも配列として保持するが、CLIの標準出力では空配列にし、同じ内容を標準エラーへ出力する。

## コマンド構成

現行の末端コマンド構成は次のとおりとする。引数はCLIヘルプと`../手順/context-statを使う.md`に記載する。

```text
context-stat stat
context-stat jinja
context-stat git diff
context-stat mcp list
context-stat mcp request
context-stat completions
```

ルートのヘルプでは、サブコマンドの末端まで含めて全コマンドを一覧できるようにする。シェル補完は `completions` で生成する。

## CLI実装

CLIの引数解析、サブコマンド、ヘルプ、補完にはClickを使用する。

- Clickは標準インストールに含めるコア依存とし、バックエンドextrasとは分ける。
- Clickのコマンドグループで、`git diff` や `mcp list` のようなサブコマンド階層を定義する。
- `--backend`、`--text-tokenizer`、`--image-tokenizer`、`--allow-online`、`--format`、`--metrics`などcontext-stat共通のオプションは、ルートコマンドのサブコマンドより前で指定する。
- `--sort`は`path`、`tokens`、`bytes`、`characters`、`lines`、`max-line-length`、`image-tokens`、`width`、`height`、`frames`、`path-length`から選択する。計測項目によるソートでは、その項目を`--metrics`にも指定する。値がない対象は最後に置き、同値の場合はパスの昇順で安定化する。
- `--order`は`asc`または`desc`とし、既定値は`asc`とする。tableとJSONは全ノードを同じソート規則で並べ、treeは同じ比較規則を使って各階層の兄弟を並べる。
- サブコマンド固有のオプションと引数は、サブコマンドの後で指定する。
- `-p`/`--parallel`はルート共通オプションとしてサブコマンドより前に置き、statのファイル読み込み、計測、ファイル単位コマンド実行のワーカー数を指定する。既定値は1、0はCPU数による自動設定とする。MCPの通信は逐次実行する。
- 並列実行しても結果と診断の順序は決定的にする。
- Clickのヘルプ生成と入力検証を使用する。
- ルートヘルプに末端コマンドまで一覧する要件は、Clickの標準表示に任せず、アプリケーション側で補う。
- `completions` はClickのシェル補完機能を利用して、指定されたシェル向けの補完スクリプトを出力する。
- 選択式の追加トークンバックエンドは遅延して読み込む。tiktokenとMCPクライアント機能は標準依存として常にCLIから利用できるようにする。
- Git差分の引数はClickの未知引数許可機能による素通しにせず、専用パーサーに渡す。専用パーサーの結果からGit実行用argvを生成する。
- Clickの依存範囲は`pyproject.toml`の`click>=8.4,<9`で定義する。
