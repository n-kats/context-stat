# context-stat設計案

## この文書の扱い

この文書は、設計レビューで見つかった未決事項に対する候補案を整理した検討メモである。正規の仕様や確定した設計ではない。実装着手前に、候補を採用、修正、または取り下げる。

確度は次の意味で使う。

- 高: 既存の要件と一般的な実装境界から大きく外れないと考えられる。
- 中: 実装しやすいが、依存ライブラリまたは出力要件の確認が必要である。
- 低: 複数の妥当な案があり、利用例を見てから決めるべきである。

## 1. 全体構造の候補

### 推奨案

当面は、現在の設計書にある細かなファイル分割をそのまま先に作らず、次の程度の境界から始める。

```text
src/context_stat/
  __main__.py
  cli.py
  application.py
  domain/
    content.py
    measurement.py
    report.py
    policy.py
  adapters/
    filesystem.py
    process.py
    templating.py
    git.py
    token.py
    image.py
    mcp.py
  output.py

tests/
  unit/
  integration/
```

責務が増えた時点で、`application.py`をコマンドごとに分割し、`adapters/mcp.py`を設定、SDK、計測記録へ分割する。最初から空の`__init__.py`や一クラス一ファイルを大量に作らない。

確度は中。機能数を考えると最終的な分割は必要だが、現段階の設計書にある分割は実装前の仮想的な境界が多く、変更コストを上げる可能性がある。

### 依存方向

```text
cli
  -> application use case
       -> domain ports
       -> adapter implementations
       -> MeasurementService
            -> TokenCounter port
            -> ImagePolicy port
       -> MeasurementReport
  -> OutputRenderer
```

`domain`はClick、MCP SDK、Git、Jinja、トークナイザーに依存しない。`application`が依存性を組み立て、`cli`はClickの値を`MeasurementOptions`へ変換するだけにする。

## 2. 計測対象のデータモデル候補

### `ContentItem`

`ContentItem`のpayloadに、単純な`str`または画像バイト列を直接入れるのは避ける。入力元によってバイト列の所有者とデコード方法が変わるためである。

候補は次のような型である。

```text
ContentItem
  id: ItemId
  origin: Origin
  label: str
  payload: TextPayload | ImagePayload | StructuredPayload
  metadata: Mapping[str, Scalar]

TextPayload
  raw: bytes
  text: str | None
  encoding: str | None
  decode_status: exact | failed

ImagePayload
  source: ByteSource
  media_type: str | None
  metadata: ImageMetadata | None

StructuredPayload
  value: JSONValue
  representation: str
```

`TextPayload.raw`はバイト数の根拠、`text`は文字数・行数・テキストトークン数の根拠にする。UTF-8でデコードできない場合は、バイト数だけを確定値として返し、文字数とトークン数は計測不能にする案を第一候補とする。エンコーディング指定を追加するかは後で決める。

`ImagePayload.source`はファイルパスまたはメモリ上のバイト列を隠蔽する。MCPのbase64画像とローカル画像を同じ画像計測器へ渡せるが、巨大な画像を常にメモリへ保持する必要はない。

### `ContentBundle`

GitとMCPは単一のテキストだけでは表現しきれないため、入力元からの返却値を次のようにする。

```text
ContentBundle
  items: Sequence[ContentItem]
  facts: Mapping[str, JSONValue]
```

Gitでは、patchを`ContentItem`にし、変更ファイル数、追加行数、削除行数、ファイル別統計を`facts`または専用の`GitDiffFacts`にする。MCPでは、送信側と返却側を別のbundleにする。

確度は中。共通の計測器へ流しながら、GitやMCP固有の構造を失わないための妥協案である。

## 3. 計測結果と確度

### `MetricValue`

数値だけを返すと、厳密値と推定値と計測不能を区別できない。候補は次の形である。

```text
MetricValue
  value: int | float | None
  precision: exact | estimated
  measurement_status: measured | unsupported | failed
  method: str | None
  reason: str | None
```

テキストのバイト数、文字数、行数は通常`exact`、Claudeのローカル画像推定は`estimated`、未確認のGPT画像式は`unsupported`とする。`method`には実際のバックエンドやモデルポリシー名を残す。

### `MeasurementReport`

JSON出力の候補は次のようにする。これは正式なSchemaではない。

```json
{
  "schema_version": 1,
  "request": {
    "model": "gpt-5.6",
    "backend": "tiktoken",
    "tokenizer": null,
    "allow_online": false
  },
  "items": [
    {
      "id": "file:README.md",
      "origin": "file",
      "kind": "text",
      "metrics": {
        "bytes": {"value": 1200, "status": "exact"},
        "characters": {"value": 900, "status": "exact"},
        "lines": {"value": 40, "status": "exact"},
        "tokens": {"value": 280, "status": "exact", "method": "tiktoken"}
      },
      "metadata": {}
    }
  ],
  "totals": {},
  "warnings": [],
  "errors": []
}
```

`MeasurementReport`自体はJSONを知らず、`JsonRenderer`が公開フィールドを明示的に変換する。`schema_version`は早い段階から付けるが、正式Schemaとして固定する前に実例を集める。

確度は中。結果の説明可能性を優先した案だが、利用者が機械処理する最終形は実際のコマンド結果を見て調整する。

## 4. モデルと画像ポリシーの候補

### `ModelProfile`

モデル名を文字列の分岐で処理せず、モデルプロファイルへ解決する。

```text
ModelProfile
  model_id: str
  family: str
  text_counter: TokenCounterSpec
  image_policy: ImagePolicy | None
  evidence: PolicyEvidence

PolicyEvidence
  source_url: str
  checked_at: date
  confidence: documented | estimated | unsupported
```

画像ポリシーは少なくとも次を持つ。

```text
ImagePolicy
  supported_media_types
  max_file_bytes
  max_width
  max_height
  max_long_edge
  max_images
  modes
  count(metadata, mode) -> ImageMeasurement
```

正式なモデルIDを指定した場合だけ確定したプロファイルへ解決する。曖昧なfamily名による自動選択は、警告付きの別機能にするか、最初は拒否する。

### 上限超過時

画像の処理結果を、次の状態で表現する候補である。

```text
within_limit
provider_normalizes
provider_rejects
requires_online_count
unsupported
```

context-statは任意の補間法で画像を作り直さない。プロバイダー仕様が内部正規化後の寸法を算出規則として定めている場合だけ、計算上の有効寸法を求める。上限を超えた画像をローカルで再現できない場合は、推定値を埋めずに状態を返す。

Claudeについては、公式のパッチ計算と上限超過時の正規化をローカルポリシーとして実装する案の確度は中である。GPTについては、公開仕様でローカル再現可能な式が確認できないモデルを`unsupported`またはオンライン計測へ回す案は、正式モデルIDと公式仕様を確認するまで低確度として扱う。

## 5. MCPサーバー接続の候補

### 範囲

MCPサーバーをcontext-statが起動または接続し、`list`と`request`を実機実行する。context-stat自身がMCPサーバーになる機能、MCP JSONの記録ファイルを入力する機能は対象外とする。

### 公式SDKを使う案

MCPのJSON-RPC、初期化、能力交渉、stdioのメッセージ境界、Streamable HTTPのセッションを自前実装せず、公式Python SDKを`McpClientAdapter`の内部で使う。

```text
McpListUseCase / McpRequestUseCase
  -> McpClientPort
       -> OfficialMcpSdkAdapter
            -> official mcp SDK
                 -> stdio client
                 -> Streamable HTTP client
  -> McpExchangeRecorder
  -> ContentBundle
```

`McpTransport`をcontext-statのドメインポートとして最初から公開しない。SDKの版変更を`OfficialMcpSdkAdapter`に閉じ込める。SDKに依存しないテストは`FakeMcpClientPort`で行う。

公式仕様ではstdioとStreamable HTTPが標準通信方式であり、新規の設計では旧HTTP+SSEを追加しない案を第一候補とする。MCP SDKのメジャー版は参照時点で文書間の差異があるため、依存バージョンは実装開始時に確認して上限を固定する。

確度は中。自前でプロトコルを実装するより安全だが、SDKのAPIと版固定の検証が必要である。

### サーバー設定の候補

1つの`--config`が1つのサーバー定義を表す形式から始める。

stdioの候補:

```json
{
  "transport": "stdio",
  "command": "uv",
  "args": ["run", "server.py"],
  "env": {},
  "cwd": null
}
```

Streamable HTTPの候補:

```json
{
  "transport": "streamable-http",
  "url": "https://example.invalid/mcp",
  "headers_from_env": {}
}
```

`command`はシェル文字列ではなくargvとして扱う。HTTPヘッダーの秘密値は設定ファイルへ直接書くより、環境変数名から解決する案を第一候補とする。設定値の秘密情報、環境変数の値、認証ヘッダーをレポートへ出力しない。

確度は中。既存のMCPクライアント設定との互換性を重視する場合は、`mcpServers`を持つ複数サーバー形式も候補になる。

### online許可とサーバーの挙動

- stdio接続はcontext-stat自身のネットワーク接続ではないため、`--allow-online`なしで許可する。
- Streamable HTTP接続は`--allow-online`必須とする。
- `--allow-online`はcontext-statが直接行うネットワーク通信を制御する。stdioで起動したMCPサーバー自身が外部へ通信することまでは制御しない。
- 実行時間、サーバー起動、初期化、各リクエスト、終了待ちに上限を設ける。
- サーバーからsampling、elicitation、rootsなどcontext-statが提供しないクライアント機能を要求された場合は、許可せず明示的に未対応として終了する。

### MCPの計測単位

MCPは「LLMが生成する側」「LLMへ返す側」「プロトコルの通信量」を混ぜない。

```text
McpMeasurement
  generated:
    logical tool/resource/prompt request
  returned:
    tool result / resource content / prompt content / list definitions
  protocol:
    initialize, initialized, JSON-RPC envelope, notifications, errors
```

第一候補の合計規則は次のとおりである。

- `generated`と`returned`は別の合計を持つ。
- `protocol`は診断用に別計測し、コンテキスト合計へ自動加算しない。
- `tools/list`などの定義は、tool名、説明、inputSchemaを1つのstructured itemとして返す。
- `tools/call`などの結果は、text/image contentを個別itemに分ける。`structuredContent`がある場合は別のstructured itemにする。
- envelope全体を数えた値とcontentを数えた値を同じ合計へ二重計上しない。
- 実際のLLM生成量やAPI請求量ではなく、指定されたリクエストをLLM生成側の入力として再現計測した値であることを表示する。

確度は中から低。利用者が欲しい「LLMに入る分」に近いが、MCPホストが実際にどの形へ変換するかはホスト実装によって異なるため、`logical`と`wire`の両方を出せる余地を残す。

## 6. `--command`の実行候補

### 第一候補

Jinjaレンダリング後の文字列を`shlex.split`でargvへ変換し、`subprocess.run(..., shell=False)`で実行する。

- `|`、`>`、`$()`、シェル変数展開などは解釈しない。
- `{{path}}`は既存例のような引用符付き指定を受け付ける。
- 任意のパスを安全に扱うため、`quote`フィルターを用意し、正式な推奨形を`{{ path | quote }}`とする。
- 標準出力だけを計測対象本文とし、標準エラー、終了コード、実行時間は実行結果に分ける。
- ディレクトリ内の一部で失敗しても他の項目を計測し、最終終了コードはエラーありを示す。
- 1項目ごとのタイムアウトを設ける。

第一候補の確度は中。ユーザーがパイプやリダイレクトを必要とする場合は、将来、明示的な`--shell`モードを別扱いにする。既定でshell実行にはしない。

Jinjaファイルのレンダリングは、ファイル読み込みや任意Python呼び出しを無効にした環境を使い、未定義変数はエラーにする案の確度は中である。

## 7. Git差分と比較

### Git差分

```text
GitDiffSpec
  revisions
  pathspecs
  supported_options

GitDiffResult
  patch: TextPayload
  file_stats: Sequence[GitFileStat]
  summary: GitDiffSummary
```

Gitのargvを文字列で保持せず、パーサーの構造化結果を保存する。未対応オプションはエラーにする。Gitのpatch本文とファイル別統計は同じ`MeasurementReport`に入れるが、patch本文の合計とファイル別値の合計を混同しない。

### 比較

`ComparisonService`は2つの完成済み`MeasurementReport`を受け取る。入力元を再実行して比較する責務は持たせない。これにより、同じ入力を2回実行して状態が変わる問題を避けられる。

比較CLIの引数形式は未決のままとし、ドメイン側だけ先に`ReportComparator`として定義する案の確度は中である。

## 8. 実装前に決める順番

1. 正式なモデルIDと、各モデルのテキスト・画像ポリシーの確度を決める。
2. MCPは公式SDKの依存バージョン、stdio設定、Streamable HTTP設定を決める。
3. MCPのgenerated、returned、protocolの計測単位と合計規則を決める。
4. `ContentPayload`と`MetricValue`の形を決める。
5. `--command`をshellなしのargv実行とするか確認する。
6. JSONの実例を作り、正式Schemaを固定する。

この順番で決める案の確度は高い。先にクラス名やファイル名を固定すると、未確定の計測単位をコードへ埋め込む可能性がある。
